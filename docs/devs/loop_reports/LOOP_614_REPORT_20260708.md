# Loop614 query-level search shard recovery report

Loop614는 full375나 Loop609 degraded/recovered `109`행 runtime replay를 새로 돌리지 않았다. Loop613 completed10에서 검색이 계속 degraded였던 원인을 shard/env/image 수준에서 추적했고, 일부 running `mcp-bridge` 컨테이너가 stale env로 `presearch`를 포함해 query-level `degraded=true`를 만들고 있음을 확인했다.

## 원인

- Loop613 preflight `ok=16/16`은 `/healthz`/`readyz` 중심이라 실제 `/mcp/search` query degraded를 잡지 못했다.
- 재빌드 전 일부 shard는 `MCP_SEARCH_ENGINES=google,bing,presearch,webcrawler,naver`였고, 같은 쿼리에서 결과가 충분해도 `unresponsive_engines=[["presearch","액세스 거부"]]` 때문에 `degraded=true`였다.
- 현재 compose config와 소스 sanitize는 `presearch`를 제거하므로, running container stale state가 직접 원인이었다.

## 조치

- `COMPOSE_PARALLEL_LIMIT=16`으로 `tools/warp_shards.py up --count 16 --shards 1-16 --project-name warp-shards`를 실행해 16개 shard stack을 재빌드/재생성했다.
- `tools/audit_search_shards.py`에 실제 `/mcp/search` query probe와 forbidden engine gate를 추가했다.
- 기본 forbidden engine은 `presearch,yahoo,yahoo_news,wikidata,wikipedia`다.
- `.gitignore` 예외를 추가해 `tools/audit_search_shards.py`와 `tests/test_audit_search_shards.py`를 git 추적 대상으로 전환했다.

## 검증

- Post-rebuild env는 `MCP_SEARCH_ENGINES=google,bing,webcrawler,naver`, fallback도 `presearch` 없음으로 확인했다.
- 16-shard query audit: `docs/devs/loop614_post_rebuild_query_search_shard_audit.json`, `ok=16/16`, query probe `16/16`, degraded `0`, forbidden engine `0`.
- Loop613 대표 제목 8개 단건 probe는 모두 `degraded=false`, `possible=false`였다.
- Unit test: `tests.test_audit_search_shards tests.test_search_recovery_contract tests.test_mcp_bridge_direct_search` 통과.
- `py_compile` 통과.
