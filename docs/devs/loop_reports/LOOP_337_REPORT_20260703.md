# Loop337 Search Degraded Recovery Contract

## 요약

Loop337은 approval 회차가 아니다. Loop336에서 `11705250` public contract는 수렴했지만 search health가 `SEARCH_DEGRADED`로 남은 병목을 코드 계약으로 좁힌 회차다.

## 원인

- Loop336 로그는 두 가지 search degraded를 보였다.
  - `raw_total=0`: upstream 검색 결과 자체가 0건.
  - `raw_total=10~17`이지만 `no_hangul`/`token_mismatch`로 bridge filter 후 0건 또는 저품질: Bing/Webcrawler에서 타이머, 위키, 호텔, 금융 같은 무관 결과가 섞임.
- `/readyz`는 `searxng=true`, `headless_search=true`, `direct_search_fallback=false`로 ok였다. 즉 서비스 liveness가 아니라 provider 품질/필터 붕괴 문제다.
- 현재 실행 중인 `warp-shards-mcp-bridge-*` 컨테이너는 repo bind mount가 아니다. `docker inspect`의 `Mounts=[]`이고, 컨테이너 내부 `/app/src`에는 이번 `fallback_recovered` 코드가 없다. 따라서 이번 패치는 git 코드 계약이며 live shard에는 재빌드/재기동 전까지 적용되지 않는다.

## 변경

- `src/llm_batch/mcp_bridge/server.py`
  - raw 결과가 충분한데 bridge filter에서 거의 전부 탈락하면 direct fallback 사유를 `low_bridge_after_filter` 또는 `foreign_noise_dominant`로 기록한다.
  - 응답 메타에 `fallback_recovered`, `degraded_recovered`, `direct_search_*` 필드를 노출한다.
- `src/llm_batch/agentic_pipeline.py`
  - bridge의 direct/recovery 메타를 search cache와 public `identity.search_health`까지 전달한다.
  - public status를 `SEARCH_DEGRADED`, `SEARCH_DEGRADED_RECOVERED`, `ok`로 분리한다.
- `src/llm_batch/experts/orchestrator.py`
  - `ConversationContext.search_query_stats`에 `fallback_recovered_total`, `degraded_recovered_total`, `unrecovered_degraded_total`, `direct_search_used_total`, `direct_search_result_total`을 추가했다.
  - 검색 로그에 `direct(...)`와 `fallback_recovered`를 표시한다.
- `tools/audit_expert_run_health.py`
  - recovered degraded는 즉시 blocker로 보지 않고, `unrecovered_degraded` 또는 `SEARCH_DEGRADED` 상태만 `search_degraded_observed` blocker로 본다.
